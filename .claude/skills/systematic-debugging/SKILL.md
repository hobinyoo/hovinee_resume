# 체계적 디버깅

## 핵심 원칙

**근본 원인 조사 없이 절대 수정하지 마세요.** 증상만 가리는 임시 패치 금지 — 왜 실패하는지 이해한 뒤 고친다.

## 4단계

### 1. 근본 원인 조사
- 에러 메시지를 **끝까지** 읽는다(모든 단어가 중요).
- 이슈를 **일관되게 재현**한다(재현 못 하면 수정도 검증 불가).
- 최근 변경·로그·스택 트레이스로 증거를 모은다.
- **콜 체인을 위로 추적**해 잘못된 값의 **최초 트리거**를 찾는다 — 에러가 *나타나는* 곳이 아니라 *시작되는* 곳을 고친다.

### 2. 패턴 분석
- 올바르게 동작하는 **유사 코드**를 찾아 구현을 **완전히** 비교한다(대충 훑지 말 것).
- 작동/고장의 **차이점**과 의존성을 식별한다.

### 3. 가설 · 테스트
- 명확한 가설 하나("X 때문에 실패한다")를 세운다.
- **한 번에 변수 하나만** 바꾸는 최소 테스트로 예측→실행→검증한다.
- 틀리면 가설 수정, 맞으면 구현.

### 4. 구현
- **실패하는 테스트**로 버그를 먼저 포착한다.
- 증상이 아닌 **근본 원인**에 단일 수정을 적용한다.
- 해당 테스트 + 전체 스위트 통과를 확인한다(회귀 없음).

> **멈춤 규칙**: 연속 3회 이상 수정이 실패하면 멈춘다 — 패치가 아니라 논의가 필요한 **아키텍처 문제** 신호. 다른 영역에서 계속 새 문제가 터지는 것도 같은 신호다.

## 위험 신호 (이런 생각이 들면 멈춤)
- "빠른 수정만 하고 나중에 조사하자"
- "한 번만 더 고쳐보자"(여러 번 실패 후)
- "이게 작동해야 할 텐데"(이유 모름) · "일단 해보자"(가설 없음)

## 체크리스트 (수정 완료 주장 전)
- [ ] 근본 원인 파악·문서화, 가설 검증
- [ ] 수정이 증상이 아닌 근본 원인을 해결
- [ ] 버그 재현 실패 테스트 작성 → 수정 후 통과
- [ ] 전체 테스트 스위트 통과
- [ ] "빠른 수정" 합리화 없음, 수정이 최소·집중적
